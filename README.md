# Provider credentialing and exclusion screening

A health system cannot bill for a clinician who appears on the federal
exclusion list, and it has to check every active provider against that list at
least monthly. This repository is the screening half of that problem: the
registries, the warehouse they load into, and the matching that decides which
hits a person has to look at.

```
python3 scripts/fetch.py && python3 scripts/profile_registries.py
```

## What is real and what is synthetic

The registries are real public files, downloaded by `scripts/fetch.py` and not
committed. The OIG exclusion list, the NPI registry weekly incremental, the NPI
deactivation report and the Medicare public enrollment extract all come from
their publishers at the URLs in `screening/registries.py`.

The credentialing application is synthetic. A real one holds application
status, documents and committee dates, and no such data is public. It is
generated by `credentialing/generate.py` into a Postgres database of its own,
and every figure drawn from it is in its own section below rather than mixed in
with the registry figures.

The generator plants overlaps against the real exclusion list and writes down
what it planted. That matters more than the rows looking plausible. The thing
this platform has to be measured on is whether it finds the providers who are
on the list and leaves the rest alone, and nothing can measure that without an
answer key.

Nothing here has run against Snowflake. The configuration under `infra/` is
validated and formatted against the provider schema and has never been applied,
because this project has no Snowflake account yet. No number in this file comes
from a warehouse.

## What the exclusion list actually contains

The design below rests on one claim about the source data, so the claim is
measured first. Every figure in this section is read out of
`measurements/registries.json`, which `scripts/profile_registries.py` writes.

| Figure | Count |
|---|---|
| exclusion records | 84093 |
| records whose NPI column holds the character zero | 75169 |
| records with an NPI that passes its check digit | 8924 |
| distinct NPIs among those records | 8743 |
| NPIs appearing on more than one record | 177 |
| most records sharing one NPI | 3 |

The NPI column is populated on every row. On 75169 of them the value is the
single character zero, which is how this file says it has no NPI. That is not a null.
A column typed as a number holds a zero instead. A join on it matches nothing
and raises no error. And a check asking whether the column is populated
answers yes for the whole file.

Not one of the 8924 real NPIs fails its check digit.

### Which match tier can reach a record at all

| Reachable by | Count |
|---|---|
| exact NPI | 8924 |
| exact name and date of birth | 71437 |
| name and state only, an individual | 863 |
| name and state only, a business | 2869 |

Only the first tier may clear a provider without a person looking, so 8924 of
84093 records are auto clearable at best. The rest reach a human by design. The
last two rows are a floor rather than a tuning problem: 3732 records carry
neither a usable NPI nor a date of birth, so no threshold anywhere reaches
them.

### What the fallback key is worth

| Figure | Count |
|---|---|
| records that can form a tier two key | 79763 |
| distinct tier two keys | 78740 |
| keys held by more than one record | 997 |
| records sitting on a shared key | 2020 |
| most records sharing one key | 4 |

Two different quantities and the design needs both. The records say how many
the tier can reach. The distinct keys say how many it can tell apart. An
earlier version of this table published only the second one under a label that
read like the first, which makes the tier look narrower than it is by a
thousand records.

A key held by two records cannot clear either of them. That is a property of
the key and it is measured here before anything is matched against it, because
the same key has to separate rows against two and a half million enrolled
providers later.

### A second sentinel, in the name column

The identifier column encodes absence as the character zero. The surname
column does it too and the value is a word. Three records carry the four
character string NULL as a surname, which is a serialised null that reached the
file as text.

Three records is small and the shape is the one this whole design is built
around, so it is handled rather than noted. A surname that is that exact word
counts as absent, so no fallback key is formed from it and those records reach
a reviewer instead. They are still people and not businesses, because they
carry a given name, and `screening/leie.py` keeps those two questions apart.

NA appears as a given name on three records and is left alone. NA is a name
somebody can have and NULL is not.

## The other registries

| Figure | Count |
|---|---|
| enrollment extract rows | 3030023 |
| enrollment rows that are not valid UTF-8 | 11 |
| distinct NPIs in the enrollment extract | 2576755 |
| exclusion NPIs also in the enrollment extract | 15 |
| deactivated NPIs published | 360673 |
| exclusion NPIs also deactivated | 951 |
| registry weekly records | 31562 |
| weekly records with no entity type code | 711 |

Eleven rows of three million carry bytes that are not valid UTF-8. A strict
load aborts on them. A lenient load replaces the character and finishes, and
the field those bytes sit in is a provider name, which is what the fallback
tiers compare. So the encoding is declared per source in
`screening/registries.py` and the enrollment file format in `infra/load.tf`
names `WINDOWS1252` and leaves character replacement off.

The enrollment extract carries no status, termination or end date column. An
NPI appearing in it is an NPI appearing in it. Reading those 15 as currently
enrolled providers would need a source this project does not have, and
`screening/cms.py` records that as a constant so a later model cannot quietly
assume otherwise.

## The credentialing source, and what it is planted with

`credentialing/schema.sql` is the application's own database. Six tables, read
by this platform rather than owned by it. `scripts/build_source_db.py` creates
it, loads the generated workflow and writes the counts to
`measurements/credentialing.json`.

| Figure | Count |
|---|---|
| providers generated | 500 |
| providers carrying an identifier from the exclusion list | 40 |
| providers carrying a name and date of birth from one | 60 |
| providers carrying that name and a different date of birth | 50 |
| providers appearing nowhere in the exclusion list | 350 |
| credentialing applications | 500 |
| state licences | 500 |
| primary source verifications | 1517 |
| committee decisions | 302 |

The third row is the one that decides whether a tier is worth running. Those
providers carry an excluded person's name and a date of birth two years away
from theirs, so anything that calls them a match is matching on the name alone.
A tier that cannot separate them from the row above is a tier that clears the
wrong people.

The labels live beside the data and never in it. A credentialing application
does not know which of its providers are excluded. That is the question the
warehouse is being built to answer, and a label column in the source would
answer it for free and measure nothing.

## Tiered matching, and what each tier can be graded on

Three tiers, strongest first, and a provider is assigned to the first one that
matches. The order is the design. It decides which queue a provider lands in
and therefore whether a person has to look at them.

| Tier | What it compares | What it may decide |
|---|---|---|
| tier1_identifier | the identifier on both sides | may clear or stop without a person |
| tier2_name_and_dob | surname, given name, date of birth | goes to a person |
| tier3_name_state | surname, given name, state | goes to a person |

Measured against the planted sample. The answer key's positive class is "this
provider is the excluded person". So the near miss bucket is a negative. Same
name, and a date of birth two years and a day away. A different person.

| Figure | Count |
|---|---|
| providers in the sample | 500 |
| flagged by the identifier tier | 40 |
| flagged by the name and date of birth tier | 60 |
| flagged by the name and state tier | 50 |
| providers cleared with nobody looking | 350 |
| excluded providers nothing flagged | 0 |

The two stronger tiers reach precision 1.00 and the cascade reaches recall
1.00, and neither number is worth much. The sample was planted by the same
repository that is being graded, so every provider those tiers can find was
put there to be found. The number that carries information is the one that got
worse.

### The tier that justifies the design fired once in 500

The name and state tier reads a state. The credentialing provider table has no
state column. The state is on the licence, and the generator was drawing it
from four facilities, so a provider planted against an exclusion record in
California was given a licence in New York.

Both arms are in `measurements/matching.json` and the control is the behaviour
this repository shipped the day before.

| Arm | Flagged by the name and state tier | Near misses cleared with nobody looking |
|---|---|---|
| state planted from the exclusion record | 50 | 0 |
| state drawn from the facilities | 1 | 49 |

Read the cascade's precision across those two rows. It falls from 0.99 to 0.67.
The better figure belongs to the arm where the review tier reached one provider
in five hundred, and where forty nine people who look like an excluded person
were cleared with nobody looking. A precision figure read on its own pointed at
the wrong design.

An answer key planted on two fields cannot grade a tier that reads three. The
state is planted now and `credentialing/generate.py` keeps the facility draw
behind a flag so the arms stay comparable.

### What a review tier has to be graded on

Graded as a classifier for "is this the excluded person", the name and state
tier scores zero precision and zero recall. Both are right and both are
useless. Nothing it flags is the excluded person and everything whose date of
birth agreed was already taken by the tier above it.

The question it exists to answer is how many of the people who look like an
excluded person it stopped from being cleared. That is 50 of 50 in the planted
arm. The cost side is the providers who appear nowhere in
the list and were sent to a person anyway. That is 0 here. The 0 is a property
of the generator rather than of the tier. Its unrelated providers draw their
surnames from a pool filtered against every surname in the file, so no name
tier can reach them at all.

### The same tiers in SQL, compared pair by pair

The measurement runs in Python and the platform runs SQL, so both exist and
both are compared. `int_screening__match_candidate` is pair grained for that
reason, and the comparison is over the whole sample rather than over the seeds.

| Figure | Count |
|---|---|
| providers compared | 500 |
| candidate pairs at the strongest tier | 150 |
| pairs only in the SQL | 0 |
| pairs only in Python | 0 |
| providers whose tier disagrees | 0 |

That comparison is not decoration either. Its first run disagreed on 103 of
the 150 pairs while agreeing on the tier for all 500 providers. The SQL was
publishing the exclusion list's absent identifier sentinel, the character zero,
in the column naming the record a match reached. Anything joining downstream on
that column would have joined to every record that carried no identifier, which
is the defect this whole repository is built around, in the column that
publishes a match. The staging model is allowed to carry the sentinel with its
flag beside it. A matching model's identifier column is an answer and not a
transcription, and a macro now nulls it there. The seed suite passed throughout.

## Attribute history, and what a screening is still worth

A screening answer is only as current as the attributes it read. The
credentialing application overwrites a provider in place, so once a surname or
a date of birth has moved there is nothing left to say what the matcher
compared against. Two snapshots in `transform/snapshots/` keep that history.
One holds the four provider columns the tiers read. One holds the licence,
because the state the third tier reads lives there rather than on the provider.

`int_screening__screening_currency` puts the three ways a screening retires in
one place. The window, which is thirty days because the exclusion list is
republished monthly. The file, because a cycle re-run against an old download
produces screenings dated today against a digest that has been replaced. And
the attributes, which is the one that needs history to see at all.

Three checks read that model. The one that would stop a release is
`assert_no_active_provider_is_outside_the_screening_window`, and a provider
nobody has ever screened fails it, which a rule written as a date subtraction
quietly passes.

### The strategy that records the wrong changes

The cheaper snapshot strategy trusts the application's own `updated_at`. Both
strategies run over the same table and the same three changes in
`scripts/measure_history.py`, so the difference is measured rather than argued.

| Strategy | Recorded a new version for |
|---|---|
| check, on the columns a tier reads | 1, 5 |
| timestamp, on the application's clock | 3, 5 |

Providers 1 and 5 are the two whose matched attributes moved. The timestamp arm
missed provider 1, whose surname changed without the clock moving, which is
what a direct update or an absent trigger looks like. It recorded provider 3
instead, where the column that moved was a specialty no tier reads. The cheaper
strategy got both directions wrong at once on a three row change set.

Before the changes no check failed. After them exactly one did, and it was
`assert_no_active_provider_was_screened_before_their_attributes_moved`.

### A snapshot that reads a model cannot run on its own

The snapshots read the staging models rather than the raw tables. The raw
identifier column arrives with padding around it on some rows, and a version
recorded for padding appearing is a version no tier can act on. The cost is an
ordering rule, and a monthly cycle written to snapshot first and transform
second fails on a fresh warehouse.

```
Catalog Error: Table with name "staging.stg_credentialing__provider" does not exist because schema "staging" does not exist.
```

A combined build orders it correctly. Running the snapshots on their own does
not.

## Replication, and the setting that is not in any configuration

The credentialing database reaches the raw layer through a replication
connector configured in `infra/fivetran.tf`. Nothing has been applied. There is
no account for it.

The connector offers two ways to detect a changed row. One tails the write
ahead log through a logical slot. The other finds changed rows through the
system columns, so it cannot see a row that appeared and went between two
syncs. The provider's own schema describes the first as replicating new,
changed and deleted rows.

What neither setting controls is what a delete actually carries. That is
decided by the source table's replica identity, which appears in no connector
field and in no connector setting. `scripts/measure_replication.py` measures
it against a real server. One insert, one update and one delete per setting,
then the slot is drained and every message is read.

| Table | Replica identity | Primary key | What reached the log |
|---|---|---|---|
| pk_default | default | yes | insert, update, delete carrying the key |
| pk_full | full | yes | insert, update, delete carrying the whole old row |
| pk_index | index | yes | insert, update, delete carrying the key |
| no_pk | default | no | insert only |
| identity_nothing | nothing | yes | insert only |

The last two rows are the surprise and it runs the other way from what you
would expect. The delete did not go missing quietly. Postgres refused it.

```
cannot delete from table "no_pk" because it does not have a replica identity
and publishes deletes
```

So adding a table to a publication takes something away from the application
that owns it. A table with no replica identity stops accepting updates and
deletes, and the error is raised in the credentialing system rather than in the
warehouse. The first person to notice is a credentialing coordinator whose save
button stopped working, in a system nobody changed.

Two consequences, both in `credentialing/schema.sql`. Every table carries a
primary key. And the two tables where a missed delete changes a screening
answer declare the full replica identity, so a delete publishes the whole old
row rather than the key alone. Those two are the committee decisions and the
licences. A rescinded approval left in place reads as an approval that still
stands, and a provider cleared on a deleted licence is cleared on nothing. Both
clear somebody who belongs in the review queue, which is the one direction of
error this platform exists to prevent.

`credentialing/catalog.py` grades the source database for exactly that. It
reads the catalog rather than the DDL, because the thing it has to check is the
state of the running database and not the text of a file.

## Staging, and the marker that is usually null

`transform/` is the dbt project. The staging models are the first place the
replicated tables are read, and two things there are not cosmetic.

The connector marks a deleted row with a boolean column rather than removing
it. The only state that column reliably carries is true on a row that was
deleted. A row that was never deleted can arrive as false or as nothing at all,
and that is the whole problem. The obvious filter reads the absence as unknown
and drops every live row with it.

```sql
where not _fivetran_deleted                      -- drops every row with no marker
where coalesce(_fivetran_deleted, false) = false -- the one the models use
```

The seeds under `transform/seeds/` carry all three states on purpose, and a
test fails if the two spellings ever stop disagreeing on them. A fixture where
the column happens to be populated makes the difference invisible, which is how
this gets committed.

The second thing is the identifier. It stays text, its absence is published as
its own boolean beside it, and it is trimmed rather than merely cast. An
identifier arriving with padding around it is not empty and is not the
sentinel, so it passes every completeness check and joins to nothing. That one
was found by reading the staging output row by row rather than by any test.

### What a parse against the warehouse adapter is worth

The models run against the local engine and are only parsed against the
warehouse one. A parse opens no connection, so it is the only claim about the
warehouse this repository can make, and the claim is narrow. It says the
project is well formed against that adapter and that every relation name
resolves where it was meant to. It does not compile the warehouse SQL, which
has therefore never existed anywhere.

`scripts/measure_targets.py` parses once per target and records what each one
resolved. Both targets write the same manifest file, so each parse runs against
a cleared directory and its answer is read before the next one starts. Reading
after both have run compares one target against itself and reports agreement.

That comparison is not decoration. It found the staging models resolving into
`SCREENING_RAW.staging_staging`, which is the wrong database and a schema name
written twice. Both targets produced a name, neither name was checked against
anything, and a validate has nothing to say about either. The schema is now set
once by a naming macro and the sources name the raw database rather than
following the target they are about to write into.

## Architecture

```

        |              |              |                    |
        +--------------+------+-------+--------------------+
                              |                      credentialing application
                      cloud storage prefix                 own Postgres
                              |                                 |
                  external stage, one file format      logical slot, publication
                      per source encoding                       |
                              |                        replication connector
                 SCREENING_RAW.REGISTRY  <-- pipe              |
                              |                     SCREENING_RAW.CREDENTIALING
                              +-----------+-----------+
                                          |
                           staging, deletion marker handled
                             and the sentinel kept apart
                                          |
                              SCREENING_ANALYTICS marts
                                          |
                              +-----------+-----------+
                              |                       |
                      exact identifier only      everything else
                        cleared without a         reaches a person
                         person looking
```

Four account roles rather than one. Loading writes the raw layer and reads
nothing in analytics. Transforming reads raw and writes analytics. Analysis
reads the marts with identifiers redacted. Review sees identifiers whole for
one facility. The roles exist in `infra/roles.tf` and what each one can do is
in `infra/grants.tf`, because a role is only a name until something is granted
to it.

## Who reads what, and what a redaction leaves behind

Four roles. The loader writes raw and reads nothing in analytics. The
transformer reads raw and writes analytics. The analyst counts the queue. The
reviewer works it, which means deciding whether this provider is that excluded
person.

The obvious design masks the identifier, the name and the date of birth on the
review queue. It leaves the pair grained candidate relation alone. It protects
nobody who was matched.

Both match joins are equalities on the columns the mask would hide. The first
tier joins the provider identifier to the record identifier, so on a first tier
row `matched_npi` is the provider's own identifier. The second tier forms its
key out of the surname, the given name and the date of birth with pipes between
them, so `matched_fallback_key` on a second tier row is all three values. The
third tier joins on the surname and the given name only, and publishes the same
key, so it gives back two of the three. Nothing in either column name says any
of this.

Measured over the whole sample in `measurements/access.json`:

| pairs the identifier tier formed | 41 |
| pairs where the matched identifier is the provider's own | 41 |
| pairs the name and date of birth tier formed | 61 |
| pairs where the matched key is the provider's whole identity | 61 |
| pairs the name and state tier formed | 51 |
| pairs where the matched key is the provider's name | 51 |

Every pair, in all three tiers. The withheld set is therefore the closure over
every column set that recovers the quantity, which is what
`screening/access.py` declares and what `tests/test_access.py` grades in both
directions against the measurement. A recovery the measurement finds and the
design does not declare is a column reading whole that nobody meant to publish.
A recovery the design declares and the measurement never found is a rule
resting on somebody's reading of a join.

The third tier was the second kind. The condition had been written as the
second tier alone, which is what reading the join that forms the key gives you,
and the measurement is what put the third tier in it.

### A per column mask cannot answer a per row question

`matched_npi` is the provider's own identifier on a first tier row and a
different person's record on the others, and a reviewer needs it on the others.
Masking the column outright is correct and costs the reader the record on every
row. The provider's conditional masking form takes the deciding column as a
second argument through `using` at the attachment, so the answer can be per
row. That field is described in `terraform providers schema -json` and its
flags say only that it is optional.

### What the provider can and cannot attach a policy to

A row access policy attaches to a view or to an iceberg table in the
`snowflakedb` Snowflake provider at 2.23.0 and to nothing else. `snowflake_table` carries
no `row_access_policy` block at any nesting level. So the raw layer cannot be
row filtered declaratively at all, and the relations the models build are dbt
views that dbt creates and drops on every run.

Terraform declaring a view dbt also declares is two owners for one object. So
the models stay granted to the transformer alone, and the reading roles are
granted on secure views in a `REVIEW` schema that Terraform owns. That is one
more layer than the obvious design and it is the only one that is expressible.

### A provider with no facility

The reviewer's row filter is keyed on the facility, which comes from the active
application. A provider with no active application has no facility, so a filter
with only the assigned branch reaches them from no reviewer at all. That is the
same disappearance as the state tier being unable to reach a provider with no
licence.

An unscoped row goes to every reviewer instead. The cost is duplicated work on
a small bucket and the count is published rather than discovered. The cost of
the other answer is a provider screened against nothing who is never looked at,
and from the outside an empty queue and a queue nobody can see are the same
thing.

### What each role sees, on the committed fixture

| rows in the review queue | 8 |
| rows the reviewer reads in the review queue | 7 |
| rows in the candidate relation | 5 |
| rows the reviewer reads in the candidate relation | 4 |
| queue rows with no facility | 4 |

The analyst reads every row and no names. The reviewer reads every name and
fewer rows, which is one exemption going each way, and a design treating
exemption as one switch would have got one of them wrong.

Two arms, because the first one was a reimplementation.
`scripts/measure_access.py` builds the relations in Python and
`scripts/measure_access_warehouse.py` runs the view statements against the
models in duckdb. The Python arm came back with four
candidate rows where the warehouse has five, because it built the relation out
of the tier cascade and the model unions all three tiers. The suite compares
the two arms row by row now, over the columns the warehouse manifest names.

## The gate on the configuration

`terraform validate` reads a value and asks whether the provider accepts it.
Almost every argument that decides whether a Snowflake object does anything is
optional, so it cannot fail on an argument nobody wrote. A warehouse with no
`auto_suspend` runs on the account default. A resource monitor with only a name
has no quota, no triggers and no recipients. A grant naming neither
`privileges` nor `all_privileges` grants nothing. A pipe without `auto_ingest`
waits to be asked. Every one of those validates.

So `screening/tfrules.py` carries one rule per capability and each rule fires
when the element that makes the capability real is absent. The rules run in the
test suite rather than as a plan, because the suite runs on a clone with no
cloud account. `tests/fixtures/infra_bad/bad.tf` is a configuration written to
break every one of them, and the suite fails if any rule stays silent on it.

Two defects in this configuration came out of `terraform validate` and neither
was a wrong value. The provider cannot connect on a warehouse this
configuration creates, which is a cycle. And `frequency` and `start_timestamp`
on a resource monitor are both listed as optional attributes while the provider
refuses either one alone, with the pairing stated in the description text
inside the schema rather than in its required flag. I read the required flags
first and missed the second one entirely.

## Running the checks

```
python3 -m pip install -r requirements.txt -r requirements-dev.txt
python3 tests/run_all.py
```

The matching measurement needs the downloaded exclusion list and no database.
It regenerates the workflow in memory, so the grading does not wait on Postgres
having loaded anything, and it falls back to the committed fixture when the
download is absent.

```
python3 scripts/measure_matching.py
```

The transform project is a separate toolchain and a separate requirements file.
It needs a server for the source database and neither the suite nor the readers
need any of it.

```
python3 -m pip install -r requirements-transform.txt
python3 scripts/build_source_db.py --dsn "$CREDENTIALING_DSN"
python3 scripts/measure_replication.py --dsn "$CREDENTIALING_DSN"
cd transform && dbt seed --target duckdb && dbt build --target duckdb
cd transform && dbt parse --target snowflake
```

The build is one command on purpose. The snapshots read the staging models, so
running them before the models that feed them fails. The attribute history
measurement is separate and it writes to a database of its own, because a
measurement that plants its fixtures in the shared one poisons every other
measurement that reads it.

```
python3 scripts/measure_history.py --database /tmp/history.duckdb
```

The access measurement has two arms and they run in different places. The
Python one needs the download and no database. The warehouse one reads the
database a build left behind, so it runs after a build and only where duckdb is
installed.

```
python3 scripts/measure_access.py
python3 scripts/measure_access_warehouse.py --database transform/target/screening.duckdb
```

The suite needs no downloads. Every check reads a committed fixture, and
`tests/fixtures/PROVENANCE.md` says how each one was built and what was changed
on the way in.

It does need both requirements files. The second one carries a parser used to
grade the configuration reader against an independent reading of the same
files. Those checks fail rather than skip when it is missing, because a check
that goes quiet without its dependency reports clean on a machine that cannot
run it.

## Known limitations

The replication connector has never run. The configuration is written against
the provider schema version it pins and has never been planned or applied,
because there is no account for it and no Snowflake account to land in. What is
measured is the behaviour of the source database under logical replication,
which is the half that does not need either account.

The models have been built against a local engine and parsed against the
Snowflake adapter. Parsing resolves the dispatch and the materialisation
without a connection. It does not compile the Snowflake SQL, which has
therefore never existed anywhere, and no check in this repository implies it
has.

The staging models are graded against a nine row fixture and a handful of
seeds. The behaviour they are graded on is the handling of a null deletion
marker and a sentinel identifier, which is a property rather than a volume, so
the fixture size is the right size for it. Nothing here says how any of this
behaves at the scale of the enrollment extract.

The planted overlaps are the answer key and the matcher is graded against
them. Both were written here, so every precision and recall figure above is a
statement about a sample this repository built. The figure that survives that
objection is the one that got worse when the generator was corrected, because
nothing was tuned to make it worse.

Nothing has been applied to Snowflake. The configuration is correct against the
provider schema version it pins and unproven against an account. There is no
Snowflake account identifier and no service user for this project yet, so the
deploy workflow has nothing to authenticate as.

The workflow in `.github/workflows/ci.yml` has never executed. The checks on it
read the names of the scripts it calls and the arguments it passes. They cannot
see whether the state one step leaves is the state the next one needs, which is
the defect that kind of file usually has.

The monthly NPI full file is 1079 MB and nothing here downloads it. The weekly
incremental shares its record layout, so the readers and the eventual staging
models are written against the weekly one and the full file is a larger input
to the same code. That is an assumption about the layout and it has not been
checked against the full file.

The matching has no threshold and no fuzzy comparison in it. Every tier is an
equality on columns that were cleaned first, which is why a near miss two years
and a day away is refused rather than scored. A real screening platform needs
an approximate name comparison and this one does not have one, so the review
queue here is smaller than a production queue would be.

The state tier reads a state that lives on the licence. A provider whose
licence has not arrived yet, or whose licence row was deleted, cannot be
reached by it at all. That is the same deletion that removes the basis for a
clearance, and it removes the provider from the review tier in the same moment.
Nothing here handles that yet.

The attribute history is graded on three changes applied to a seeded fixture.
What that measures is a property of the two strategies rather than a volume, so
the fixture size is the right size for it. Nothing here says what either
strategy costs on a provider table with millions of rows, and the check
strategy compares a column list on every row of every run.

The pipe needs a notification integration that does not exist, so it would fail
a plan for a second reason beyond the missing account.

No masking policy and no row access policy has ever been applied or evaluated.
Everything above about what each role sees is the design being applied to the
relations by code in this repository, and the configuration being graded
against that design. A policy body is SQL inside a string that `terraform
validate` does not read at all, so none of these bodies has been parsed by
anything, let alone run by Snowflake.

The reviewer to facility mapping is a table this configuration creates and
never populates, because a reviewer joining is an operational event rather than
a configuration change. Until somebody loads a row, every reviewer reads the
unscoped rows and nothing else. That is a visibly empty queue rather than a
silently full one, which is the right way round, and it is still a bootstrap
state nothing here handles.

The row filter is graded on the committed nine row fixture. What it measures is
that the predicate separates three facilities and an unassigned bucket, which
is a property rather than a volume. Nothing here says what the policy costs on
a queue with a million rows in it, and a row access policy is evaluated on
every query against the relation.

The warehouse arm runs under duckdb and the policies are written for Snowflake.
The relation contents are engine independent and the enforcement is not, so the
arm grades what the views select and nothing about what the policies would do
to it.
